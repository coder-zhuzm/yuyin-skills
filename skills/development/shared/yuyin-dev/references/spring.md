# Spring 业务与接口实务

仅在当前项目使用 Spring，且任务涉及接口调用链、持久化、事务或相关测试时读取。版本、构建命令、数据访问方式、目录与返回约定从源码和配置确认；下面是检查依据，不是迁移模板。

## 先追踪一条实际调用链

- 从请求映射、参数绑定、鉴权与校验，追到 Service，再到项目实际的 Mapper/XML、Repository 或其他客户端；记录影响此次行为的 SQL、配置、异常转换和响应。
- 查同类接口的 DTO、分页、错误码与异常处理方式；按现有契约修改，检查调用方兼容性。不要因为示例习惯把 MyBatis 换成 JPA，或把已有响应包装改成另一套标准。
- 只改任务涉及的层。若行为已在现有扩展点实现，复用该处，不补齐一套没有实际职责的 Controller-Service-Repository 分层。

## 按实际副作用检查一致性

| 项目证据或问题 | 判断与可观察验证 |
| --- | --- |
| 一个业务动作写多条记录 | 确认事务入口实际经过代理、事务管理器与传播配置；异常被捕获、同类内调用或跨线程时不能仅凭 `@Transactional` 推断回滚。用故障点验证应一起回滚的数据 |
| 数据库写入后调用外部服务或发消息 | 区分本地事务与外部效果；核实失败、超时和重试后状态。仅在已有机制或任务需要时使用补偿、outbox 等方案，本地事务不自动撤回外部操作 |
| 创建、扣减等请求可能重复或并发 | 先确认重复请求的业务语义、幂等键范围与有效期，再检查现有唯一约束、条件更新或幂等记录；验证重复与并发调用后的记录、计数和返回结果，不以一次查询后判断存在代替并发保证 |
| 校验、业务异常或依赖失败 | 核实异常是否按当前契约传播、映射与记录，失败路径不能返回成功或吞掉上下文；日志与响应沿用项目的敏感信息处理规则 |
| 查询涉及分页与排序 | 确认参数、总数、稳定排序及筛选约定；检查空页、越界和联表后的重复记录。需要判断性能时查看实际 SQL 与执行证据，不能只看接口耗时或臆测索引 |

常见误判：

- 错：加上事务注解就宣称失败会全部回滚。对：确认调用方式和异常规则，用真实数据库场景验证失败后的状态；Mock 的交互断言不能证明提交或回滚。
- 错：先查“未存在”再插入，就认定接口幂等。对：核实已有并发约束，按业务约定验证重复请求结果；若缺少必要保证，先说明最小方案和兼容影响。

## 选择能证明行为的测试层次

沿用项目已有框架与测试资源，不自动增加数据库容器或新测试体系，也不设统一覆盖率门槛。

| 要证明的行为 | 适合的验证与证据边界 |
| --- | --- |
| Service 分支、计算与错误处理 | 使用已有单测，通过公共方法检查输入与结果；Mock 只替代边界，不用被测实现生成预期值 |
| 请求绑定、校验、序列化与异常映射 | 使用已有 Web 层测试；若关闭安全过滤器或替换依赖，明确尚未验证真实鉴权或下游行为 |
| Mapper SQL、唯一约束、事务与并发 | 使用与行为相关的数据库集成测试；核实数据库方言、连接和事务设置，替代数据库结果不能自动代表生产数据库 |
| 完整接口契约或跨服务行为 | 运行实际请求并检查响应、持久化状态与相关副作用；区分本地集成、Mock 与真实依赖联调 |

先复现风险，再验证修复；测试未运行、环境缺失或只覆盖一层时报告具体缺口。涉及事务、并发、权限或数据隔离的修改，交付前重点审查其失败路径与验证证据。
