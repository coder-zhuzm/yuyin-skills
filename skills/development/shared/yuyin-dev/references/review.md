# 审查与交付

先读原始请求、验收条件、适用项目规则与验证基线。按用户要求确定审查范围：当前工作区包含已暂存、未暂存及相关未跟踪文件；分支审查先核实比较基准与提交范围。说明范围，区分已有改动与本次改动，不能只看分支 diff 而漏掉尚未提交的工作。
检查：
- 需求覆盖：逐项对应实际行为和验证证据；指出遗漏、与约定不一致或尚未验证的验收条件。
- 正确性：正常/异常、边界、并发、状态与原目标。
- 范围：夹带重构、升级、开关与额外功能。
- 架构：业务泄漏到通用层、是否重复现有能力；抽象是否把复杂度封装在简单接口后。假设删掉包装层，复杂度会消失还是散落到调用方？只搬代码、增加跳转而不减少决策负担的抽象应说明具体成本，不凭文件数量判断好坏。
- 数据接口：权限、隔离、校验、幂等、兼容、迁移与回滚。
- 验证：实际覆盖风险，有无删断言、跳测试、降阈值。
- 资源：无限重试/队列、N+1、并发与超时；性能问题要有证据。
- 真实性：完成/通过是否有运行结果。

按阻塞、必须修复、建议、小项排序。每项写位置、条件、后果和最小修正。
没有实质问题就直说，不凑数量。
轻微文案/样式用差异和页面验证；权限、数据、消息发送验证关键失败。
独立审查只在已有授权和能力下使用；自审不能宣称独立审查。
交付四句：行为变化、关键原因、验证结果、限制。
部署/推送不自动发生，也不要对已获明确授权的动作反复确认。
