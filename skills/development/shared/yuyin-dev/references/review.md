# 代码审查与问题判定

先读原始请求、验收条件、适用项目规则与验证基线。工作区审查包含已暂存、未暂存及相关未跟踪文件；分支审查先核实比较基准与提交范围。区分已有改动与本次改动。

## 先判定，再排序

对每项候选问题先列出三件事：要求的证据位置、实际违背该要求的代码位置、可触发的后果。要求来自用户验收、项目规则、已约定公共接口或实际调用方；审查惯例是检查线索，本身不扩展代码承诺的输入、能力或 SLA。

- **确定缺陷**：适用要求、实际违背和触发路径均有证据。报告须引用要求与代码双方的位置，再说明影响和最小修正。
- **条件性风险**：结论依赖尚未确认的输入、环境、负载或外部机制。写明“在什么前提下会发生什么”及核实方式，保留前提未知的状态。
- **可选改进**：另一种设计或能力可能有收益，但当前没有已证实的要求被违背。说明取舍与成本，交由任务优先级决定。

没有满足第一类条件的问题时，明确“未发现已证实缺陷”，再按需要附条件性风险、建议与验证缺口。严重程度只对已成立的问题排序，不因需要写报告而补足问题数量。

涉及语言或框架运行时语义时，先用对应实现、权威资料或最小复现核实，再断言崩溃、未处理异常或数据丢失等后果。无法查证时，将这部分结论保留为待验证假设。

## 按改动选择检查

- 需求与范围：实际行为、遗漏、夹带重构、升级或额外功能。
- 正确性与接口：已约定的输入、错误传播、权限、隔离、并发、幂等及兼容；区分源码判断、Mock 与真实联调。
- 架构：复用现有能力，业务归属清楚；抽象应减少调用方的决策负担，只搬代码、增加跳转时说明具体成本。
- 验证与资源：测试是否覆盖真实风险，有无删断言或跳过失败；性能、重试、队列及超时结论需要对应证据。

交付先给审查结论与范围，再按上述性质和严重程度列问题。每项保留依据、条件、后果和最小行动。自审与独立审查如实区分，未运行的检查不报告为通过。
