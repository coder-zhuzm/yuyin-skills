# 保持行为的重构

先确定要减少的具体成本：重复业务决策、过长调用链、职责混杂或难以隔离的依赖。用一个实际修改场景说明目标，避免仅以行数、文件数或设计模式作为收益。

1. 查公开入口与调用方，列需保持的返回值、异常、状态变化、调用顺序和外部副作用；记录现有有效 workaround。
2. 旧代码缺少保护时，先用公共接口补特征测试。断言覆盖当前有意保留的行为和边界，已知缺陷单独说明，区分缺陷修复与结构变化。
3. 选择最小结构改动，按依赖顺序小步推进；接口、持久化模型和依赖版本保持已确定的契约。出现新行为需求时明确拆出。
4. 用相同输入比较前后结果，检查调用方、错误传播及相关失败路径。纯搬移也要核对导出、路径、绑定和初始化顺序。
5. 审查抽象是否减少调用方的决策负担；若只是增加包装和跳转，说明保留它的实际理由。

交付补充：保持了哪些契约、消除了哪处重复或耦合、哪些特征测试证明行为一致。性能收益另需测量。
