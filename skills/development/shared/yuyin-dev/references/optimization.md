# 判断与实施优化

先区分性能、可靠性、成本、维护性和体验。“复杂”不是性能瓶颈证据。
找相关基线：延迟/SQL 次数/错误率/Token 成本/重复分支/用户场景。
没证据时提低成本测量，不用大重构代替测量。

按收益、风险、实施与验证成本排：立即改、先测、以后改、保持现状。
可读性改进描述减少的概念与分支，不虚构提升百分比。
“是否能优化”只评估；“优化一下”在明确目标范围实施。

先锁住需保持的行为。旧代码无测试又需重构时补对应特征测试，不追全仓库覆盖。
一次改一个因素，分离结构变化与新行为。同环境同输入比较前后。
模型路由比较任务质量、延迟、失败与成本，不能仅便宜就自动切生产。
RAG 先用实际问题集评测检索/答案来源，再决定是否换 embedding 或加重排。

RTK 只压缩终端输出，不等于总账单节省。先试 Git 状态、测试汇总和容器列表。
关键原始请求、堆栈、协议差异保留完整输出；缺失证据不等于无异常。
RTK 二进制安装与更新为独立操作，本包不自动下载或执行。
