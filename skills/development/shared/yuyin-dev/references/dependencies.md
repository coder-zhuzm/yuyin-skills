# 依赖升级与框架迁移

用户明确要求升级或迁移时，按该授权推进。先从清单、锁文件、运行时和调用方确认当前版本与目标范围；“评估能否升级”保持只读。目标主版本、数据兼容或停机策略无法从任务确定且影响正确性时，再集中提出决策。

1. 确认直接与传递依赖、peer/运行时约束、框架插件、构建与部署环境。查目标版本的官方发布说明和迁移指南；资料不可访问时标明尚未核实的兼容点。
2. 列出受影响 API、配置、数据格式和调用方，用最小兼容矩阵标记哪些需要一起变化。沿用包管理器与锁文件，限定到此次授权的依赖集合。
3. 先建立旧版可运行基线。分开依赖解析、API/配置适配和业务变化，采用可独立验证、可回退的步骤；执行安装或迁移前核对项目门禁与现有授权。
4. 同步清单和锁文件，检查意外升级；覆盖核心接口、失败路径、构建与启动。某层无法运行时保留该层未验证状态，本地替身不能证明真实供应商兼容。
5. 说明如何回到旧依赖、配置和数据状态。不可逆数据变化需另行确认备份、恢复边界与执行时机，业务持续写入时不能只靠回退代码承诺恢复。

交付补充：当前→目标版本、兼容改动、实际验证矩阵、回退入口及剩余风险。只修改版本号不等于升级验收完成。
