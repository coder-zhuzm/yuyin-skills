# 余音开发工作流

保留 `$yuyin-dev` 调用，也接受自然语言。根据完整请求区分评估与实施，先确认当前项目，再选择最少的相关参考。

## 开始工作

1. 读取适用的项目指令、相关源码、依赖与锁文件和 Git 状态，保留用户改动。命令、版本与架构以当前仓库证据为准。
2. 明确目标、范围和可观察验收条件。实现任务在已有授权内推进，遵守项目执行门禁；只向用户提出源码无法解答且影响正确性的产品决策。已获授权的常规步骤直接推进。
3. 从下表选择一个主要意图参考；明确跨意图时再补相关部分。通用局部逻辑可直接采用现有工具，需要框架、设计或测试专项建议时才读 [专业技能路由](references/stack-skills.md)。

| 意图 | 处理重点 | 按需读取 |
| --- | --- | --- |
| 了解或初始化项目上下文 | 只读建立项目事实与运行入口 | [context.md](references/context.md) |
| 新增、实现、修改行为 | 完成一条业务闭环 | [feature.md](references/feature.md) |

## 共用边界与交付

- 项目事实留在当前项目；沿用既有技术栈、组件和测试体系，扩展范围以本次需求为依据。任务状态默认放在对话中，项目文档只按明确请求维护。
- 只读任务保持文件与外部状态不变。推送、部署、迁移、外发及安装额外技能依据明确授权执行；已有授权持续有效。
- 验证与风险匹配：核心行为覆盖成功、边界和相关失败；小文案或样式用相应检查。跨层功能检查实际请求、数据和用户结果；测试预期来自需求或独立样例。
- 结论附对应证据：报告“通过”需有实际运行结果；判断工具、依赖或服务缺失需先检查对应环境，说明命令、结果与影响。区分源码判断、测试、Mock 和真实联调，保留失败与未验证项。
- 实施后审查 diff。交付先说结果，再给关键依据或代码位置、实际验证、限制与下一步；各意图参考只补本任务特有信息，篇幅随任务复杂度调整。
