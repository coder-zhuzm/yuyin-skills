# 余音开发工作流

保留 `$yuyin-dev` 调用，也接受自然语言。根据完整请求区分评估与实施，先确认当前项目，再选择最少的相关参考和已安装专业技能。

## 开始工作

1. 读取适用的项目指令、相关源码、依赖与锁文件、已有项目记录和 Git 状态，保留用户改动。命令、版本与架构以仓库证据为准；不要把参考项目当成当前项目。
2. 明确目标、范围和可观察验收条件。只读任务不改文件、不创建 Issue；实现任务在已有授权内推进，遵守用户和项目的执行门禁。缺少影响正确性的产品决策才提问。
3. 涉及技术实现时，读 [专业技能路由](references/stack-skills.md)，按当前栈、版本和具体任务选择。技能建议不能取代用户需求、项目事实或已经验证的有效方案。
4. 按下表读取当前意图对应的参考，不加载全部资料。已有项目的局部修改沿用其组件、持久层、目录与测试体系；迁移、重设计或新增依赖必须有任务依据。

| 意图 | 方式 | 按需读取 |
| --- | --- | --- |
| 了解或初始化项目上下文 | 先只读；文档仅在明确要求时创建或修改 | [context.md](references/context.md) |
| 新增、实现、修改行为 | 完成一条业务闭环并验证 | [feature.md](references/feature.md) |
| 分析报错、排查或修好 | 分清诊断与修复授权，复现并定位 | [bug.md](references/bug.md) |
| 能否加入、是否值得 | 只读评估可行性与取舍 | [assessment.md](references/assessment.md) |
| 解释或梳理已有逻辑 | 追踪实际调用链，不顺便重构 | [logic.md](references/logic.md) |
| 能否优化 / 优化一下 | 前者评估；后者按基线实施 | [optimization.md](references/optimization.md) |
| 审查或检查改动 | 对照 diff、验收与验证证据 | [review.md](references/review.md) |
| 交接或复盘 | 汇总已知状态与可复用经验 | [handoff-retro.md](references/handoff-retro.md) |

涉及异步副作用、外部协议、视觉交互或运行环境时，按证据选择 [技术检查](references/domains.md)。这些是条件检查，不是每个项目的必做清单。

## 实施与交付边界

- 项目事实从现有代码和记录读取。默认在对话中维护任务状态；不自动创建 `.ai-dev`、ADR 或其他文档。
- 只改与目标直接相关的内容。保留现有技术栈和已验证事实，不能将某个项目的业务规则、个人身份或单次故障写成通用要求。
- 验证与风险匹配：核心行为检查成功、边界和相关失败路径；小文案或样式修改不强制新建测试。跨层功能检查实际请求、数据变化与用户结果，构建通过不能代替 UI 或业务验收。
- 仅实际运行且结果支持的检查可报告“通过”。区分源码判断、测试、Mock 与真实联调，写清未验证范围和阻塞；不通过删除断言或跳过失败掩盖问题。
- 完成后审查 diff，报告行为变化、依据、验证结果与限制。推送、部署、迁移、外发及安装额外技能遵循已有明确授权，不由普通开发请求自动推定。
