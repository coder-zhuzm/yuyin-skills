# 余音开发工作流

接受自然语言或“初始化、功能、修复、评估、逻辑、优化、审查、交接、复盘”等前缀。
从完整请求判断意图，不能只匹配一个关键词。

| 意图 | 方式 | 按需读取 |
| --- | --- | --- |
| 初始化项目配置 | 读代码，只维护开发文档 | references/context.md |
| 新增、实现、改成、帮我修好 | 在已授权范围实现并验证 | references/feature.md 或 references/bug.md |
| 能不能加、是否值得、分析为什么 | 只读调查，不自动实施 | references/assessment.md |
| 解释现在怎么走、梳理已有逻辑 | 追踪真实调用链，不顺便重构 | references/logic.md |
| 看看能不能优化 / 优化一下 | 前者只评估；后者测基线后实施 | references/optimization.md |
| 审查、检查改动 | 读 diff 与验收条件 | references/review.md |
| 整理给别人继续、复盘 | 保存状态或提出环境改进 | references/handoff-retro.md |

只读当前任务需要的参考。处理企业微信/RPA、Java、模型网关、知识库或视觉交互，再读 references/domains.md。
不要把研究过的仓库当成用户项目，或把设计方案当成已经实现。

## 共用纪律

1. 读适用的 AGENTS.md/CLAUDE.md、.ai-dev/project.md、.ai-dev/constraints.md，检查 git status，保留用户已有改动。已有授权覆盖的普通实现持续推进，不反复确认。
2. 读相关入口、实现、类型/协议、配置和测试，找到项目内参照模式。允许充分调查，限制无关修改，不限制必要读取。
3. 从仓库确认依赖版本与真实命令：Java 读 pom.xml/Gradle wrapper；前端读 package.json 与锁文件；Python 读 pyproject/requirements。内网优先本地文档、源码、缓存、离线快照与脱敏日志。无依据接口标“待验证”，不假装查过官方文档。
4. 发现根本矛盾、偏离原目标或明显不合理，先指出并说明建议；用户明确坚持后记录取舍。可查事实自己查；仅对影响正确性且无法推断的决策提问，合并为 1–3 项并给建议。
5. 明确目标、边界和 1–3 条可观察验收条件。小改动在对话记录；跨模块/新数据模型/多会话工作才创建 .ai-dev/tasks/<task-id>.md，避免为流程制造文档。
6. 先完成一条业务闭环再扩展。限制顺手重构、过早抽象与假设性配置；最小合理修复不等于最少行数。
7. 根据风险选择相关测试、构建、启动、API/UI验证。文案和小样式不强制写测试。权限、重试、幂等、租户隔离、模型转换必须覆盖失败与回归；不得删断言、跳测试或降阈值掩盖失败。
8. 完成后审查 diff。默认单主 Agent；需要独立审查时遵守用户/仓库既有授权，不无理由启动大型多 Agent 流程，不自动联系他人。
9. 仅实际执行且有结果的检查可报“通过”。环境阻塞说明命令、错误和未验证范围。Mock 不是第三方真实联调；失败未解决就说未完成。
10. 简洁交付：改什么、为什么、验证什么、还有什么限制。用户只要下一步则只给下一步。部署、生产迁移、推送与外发遵循已有明确授权和项目规则，不能从普通写代码请求推定这些动作已获授权。

## 持续遵守的边界

- “只评估”时可运行适用只读检查，不自动创建 Issue、改业务文件或实施优化。
- 保留用户已验证的事实。网关 429 已有效 workaround 必须作为复现基线，不能无证据重说只是额度问题。
- 保留用户选定栈；必要变更说明理由。公司代码、日志与密钥不进入外部通用更新包。
- 通用流程、项目事实、临时任务状态各自维护，不把一次故障变成全部项目永久规则。

## 输出契约

评估：结论（能加/有条件/暂缓）、依据、最小方案、影响与成本、未确定点。
逻辑：入口、调用链、关键分支、状态/数据变化、异常路径和代码定位，区分事实与推断。
实施：行为变化、关键修改、验证命令/结果、未验证项；有需要时给回滚办法。
审查：严重性、位置、触发条件、后果、修正建议；无实质问题就直说。
