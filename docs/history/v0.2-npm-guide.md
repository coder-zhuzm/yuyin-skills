# 余音 Skills 管理与 npm 分发指南

日期：2026-10-11 · 当前交付 v0.2.0 · macOS/Linux · 私有仓库： https://github.com/coder-zhuzm/yuyin-skills 。

## 1. 当前真实状态

已经完成：一个开发通用 Skill、零依赖 Node CLI、离线 npm tarball、源码 ZIP、项目事实模板，以及版本切换和回滚。v0.2.0 保持原 Skill 文件内容不变，只改安装和分发。原 v0.1.0 ZIP 保留。

尚未完成：公共 npm 发布、内网 registry 发布、真实公司环境试用、专用前端/后端/全栈 Skill、生活与自媒体 Skill。这些是后续计划，不能通过预留目录宣称实现。

不要从 npm 包名误判发布状态。当前 `@yuyin-local/devpack` 是本地 tarball 的标识，未确认或占用 npm scope；`private: true` 会阻止发布。现在可用的是本地 .tgz 安装，不是网上按包名安装。

## 2. 你上班先怎么用

电脑需要已安装 Node 20+ 与 npm。推荐公司批准的受支持 LTS，不因本指南修改全局开发环境。包本身无 dependencies/devDependencies、无 install/postinstall、无需 Python、不自动联网。

Notion 不接受 .tgz 附件，因此下载本页的 v0.2.0 ZIP 并解压，进入 `yuyin-devpack-v0.2.0` 目录，里面附带 `yuyin-local-devpack-0.2.0.tgz`；也可以从本对话直接下载 tgz。然后执行：

```bash
node --version
npm --version
npm install -g ./yuyin-local-devpack-0.2.0.tgz --offline --ignore-scripts --no-audit --no-fund
```

进入一个真实项目再接入：

```bash
cd /你的项目
yuyin-dev setup
yuyin-dev status
```

默认是 Claude Code + link。Codex 单独用 `setup --tool codex`，两者用 `setup --tool both`。项目不支持软链接时用 `setup --mode copy`。已经接入的项目默认保持原工具和模式；要换模式先 detach，个人项目事实保留。

全局安装目录如果没有权限，使用个人 prefix，不先要求 sudo：

```bash
npm install -g ./yuyin-local-devpack-0.2.0.tgz --prefix "$HOME/.local" --offline --ignore-scripts --no-audit --no-fund
export PATH="$HOME/.local/bin:$PATH"
yuyin-dev setup --project "/你的项目绝对路径"
```

如果不想装全局 CLI，用源码 ZIP 解压后：

```bash
node bin/yuyin-dev.cjs setup --project "/你的项目绝对路径"
```

然后补 `.ai-dev/project.md` 的真实启动和测试命令、`.ai-dev/constraints.md` 的该项目约束，开启新的 Agent 会话。第一项只读试用：

```text
/yuyin-dev 逻辑 梳理当前项目的主流程，指出入口、调用链、重要分支和代码定位，先不改代码。
```

确认读取实际代码且没有误改，再试真实 Bug 与一个小功能。Codex 的前缀是 `$yuyin-dev`。文件检查通过不等于宿主发现 Skill；应确认命令可见和任务行为。Claude Code/Codex 与模型或公司网关仍须已可用，npm 包不会提供离线模型。

## 3. 安装后到底发生什么

| 层 | 内容 | 谁更新 |
| --- | --- | --- |
| npm 全局目录 | CLI 和包内流程快照 | npm 安装新的本地 tgz/registry 版本 |
| `~/.local/share/yuyin-dev/releases/v版本号` | 独立流程快照 | 显式 setup/upgrade 复制 |
| `~/.local/share/yuyin-dev/current` | 指向生效版本的软链接 | setup/upgrade/rollback 切换 |
| 项目 `.claude/skills/yuyin-dev` | 指向 current 中的 Skill | 初次 setup/attach |
| 项目 `.agents/skills/yuyin-dev`（可选） | 同一个 Skill | 可选 Codex 接入 |
| 项目 `.ai-dev/team-rules.md` | 指向 current 的简短规则 | setup/attach |
| 项目事实、约束、词汇、任务 | 该项目独有知识 | 项目自行维护，通用升级不覆盖 |

软链接负责文件定位，不是把多个框架能力连接起来。定制包从 Addy/Matt/agency-agents 提炼方法后重新编写；RTK 与 Ruflo 只在选型说明中出现，没有它们的二进制、Hook 或编排功能。

入口只追加受管理标记块，不替换整个 `.claude`、AGENTS/CLAUDE 文件。不覆盖用户改过的副本或非受管理同名目录。每个项目只放事实，不把公司代码/日志/密钥塞入对外通用包。

## 4. 更新和回滚的准确顺序

外网获取审阅后的新 tgz，带入内网后安装，再显式升级流程：

```bash
npm install -g ./yuyin-local-devpack-新版本.tgz --offline --ignore-scripts --no-audit --no-fund
yuyin-dev upgrade
yuyin-dev status --project "/你的项目绝对路径"
```

上面的“新版本”是占位符，替换成下载的真实文件名。使用自定义 npm prefix 时，更新也传同一 prefix。使用 `--home` 时，所有 CLI 命令传相同 home。

仅 npm 安装不会自动切换流程，这样不会在你仍开发时突然改所有项目的规则。`upgrade` 不联网，它只启用当前 CLI 包自带的版本。link 项目跟随 current，copy 项目需逐个 refresh；开启新会话读取更新内容。

```bash
yuyin-dev refresh --project "/你的副本模式项目"
yuyin-dev rollback --version v0.1.0
```

回滚版本必须已经存在于 releases。未安装过 v0.1.0 不能凭版本号下载。回滚只切换流程，不能回滚业务代码、数据库、项目约束或旧对话。`yuyin-dev --version` 为 CLI 版本，`status` 为生效流程版本，回滚后两者不同是正常的。

解除：`yuyin-dev detach --project "/你的项目"`。它保留本机项目事实与业务文件；npm 卸载 CLI 不会自动解除项目入口或删除已安装流程版本。

全体接入不是完整事务，不要并发在同一 home/项目安装。源包 manifest 检查损坏，不是可信数字签名。实际来源仍由你的下载渠道和公司分发审批保证。

## 5. 后续 GitHub 仓库怎样分类

仓库为 `coder-zhuzm/yuyin-skills`，保持私有。一个来源目录、一份 Skill，不把相同文件复制到前端/后端/全栈三处。

| 路径 | 放什么 | 当前状态 |
| --- | --- | --- |
| `skills/development/shared/yuyin-dev` | 功能、Bug、评估、逻辑、优化、审查、交接等通用开发流程 | 已有 |
| `skills/development/frontend/` | 将来的 UI、交互、浏览器验收专用 Skill | 预留 |
| `skills/development/backend/` | 将来的 API、权限、数据、事务、回调专用 Skill | 预留 |
| `skills/development/fullstack/` | 将来的跨页面、接口、数据的专用业务闭环 Skill | 预留 |
| `skills/life/` | 将来的生活信息和决策辅助 | 预留 |
| `skills/content/` | 将来的自媒体选题、调研、写作、发布前检查和复盘 | 预留 |
| `catalog.json` | 唯一源码位置、分类、适用标签与实际状态 | 已有元数据，不是安装筛选器 |
| `bin/`、`lib/` | npm 命令和管理逻辑 | 已有 |
| `rules/`、`templates/` | 简短规则与项目模板源文件 | 已有 |

目前 yuyin-dev 是“开发通用”，它适用于前端/后端，也能处理全栈任务，但不是已经实现了三个专用 Skill。catalog 标签用 frontend/backend/fullstack 表达适用范围。新的专门流程稳定后再新增，例如“Java 回调幂等检查”“Three.js 素材和交互验收”。

生活和自媒体是目录预留，本次不会把开发提示词强行套过去。后续先明确真实重复任务，再写 Skill、给代表性任务验证、更新目录和版本。

## 6. 后续维护和分发怎么做

源码 ZIP 是仓库起点：包含分类源码、工具、测试与文档，并附带已构建 tgz。建仓库时由 .gitignore 排除 tgz，不将它提交为源码。npm tgz 只包含 CLI、实际可用 payload 与使用文档，不包含预留目录或维护脚本。它不能作为完整源码仓库的替代。

外网维护副本中的流程：

1. 修改唯一源码位置，记录来源及变化；不直接编辑 payload 或 installed releases。
2. 改 package.json 的版本，更新 CHANGELOG。
3. 生成 payload，执行测试，打包并试用实际 tgz。
4. 通过公司允许的途径传入内网或发布到内网 registry。

```bash
node tools/seal.cjs
npm test
npm pack --ignore-scripts
```

当前构建器只打包一个已存在的 yuyin-dev，catalog 不会自动安装新分类。未来多 Skill 增加后，需要扩展打包和选择安装逻辑，测试全局更新对各项目的影响；不能只改目录就假定 CLI 已支持。

先用手动 tgz 最省维护。多人使用且持续更新时，再接公司现有私有 registry；它可以用 npm 的版本机制，仍保留 current 切换和回滚。公网发布另行处理：确认自己有权限的 npm scope、私有信息与许可，移除 private 防护，配置明确 registry 后发布。本次不做 npm publish；源码已归入 yuyin-skills 私有仓库。

## 7. GitHub 仓库维护清单

仓库已创建并写入首批源码；在你自己电脑继续维护时：

- 核对当前登录用户、clone 目录和远程目标是 `coder-zhuzm/yuyin-skills`，保留私有设置。
- 使用仓库源码，保留唯一 Skill 源位置；不要从 tgz 反向拼源码。
- 检查没有公司代码、真实日志、密钥、账号配置、node_modules 或 tgz 二进制。
- 跑 seal、测试、实际 npm tarball 安装验证；提交并推送，再核对线上目录和 README。
- 后续有发布授权再增加 tag/Release 或内网 registry。CI 可后续配置，当前没有自动发布工作流。

目录预留不需要创建 GitHub 空目录；里面的说明文件即可保留分类。初始化仓库不要求将 npm 包公开。

## 8. 如何选择上游，而不是把定制当成替代品

主流程优先试 Addy；需求澄清、领域术语和复盘按需试 Matt；agency-agents 取角色视角；RTK 独立作为终端输出辅助；Ruflo 等有实际多 Agent 收益再考虑。

你也可以先试附件定制包，再对照上游。它尚无证据证明优于原版；区别在于它保存了你的沟通偏好、按任务分流并提供离线管理。试用只记返工、误改、重复解释和验证结果是否更清楚，不以 Skill 数量或 Star 数判断效果。

原版上游应保存完整仓库版本快照与共享 references；本 CLI 管理自己的 payload，不是通用“安装任意仓库”工具。上游更新也不会自动合入你的定制 Skill。
