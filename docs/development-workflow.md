# 余音的开发流程

适用 Claude Code 与 Codex。安装、更新与内网用法见 [安装指南](installation.md)。Skill 内容保持 v0.2.0 原样；当前改变的是分发工具。

## 1. 根据我们的沟通做了哪些定制

这份手册使用已有对话中的偏好和工作背景。没有重新审计你的项目仓库；过去的设计方案、进度报告不能作为当前代码已实现的证据。进入项目后，以真实文件、配置和执行结果补齐事实。

| 你的习惯与背景 | 这里对应的安排 |
| --- | --- |
| 常问“能不能加”“逻辑现在怎么走”“看看能不能优化” | 默认只读评估或逻辑梳理；“实现/改成/修好”才实施 |
| 希望持续推进，少来回确认 | 可查事实自己查；仅合并询问无法推断且影响正确性的决策 |
| 希望我指出不合理需求，而不是只顺着做 | 发现根本矛盾先说明并给建议；确定取舍后记录约束 |
| 已讨论 Java/Spring/MyBatis、企业微信中间层、RPA、模型网关与知识库 | 增加这些领域的按需排查与边界提醒，先确认实际项目栈 |
| CPA/Hermes 场景已有有效 workaround | 保留已验证事实作基线，不无证据重新归因为额度问题 |
| 个人站、视觉交互项目重视具体体验 | 验收写成可观察行为；真实浏览器检查交互与视口 |
| 石像方案明确“原地补全”，拒绝石柱开场、马赛克 | 属于该项目约束，写入项目记录；不要变成所有项目通用规则 |
| 接受先用临时完整图跑通 MVP，再替换素材 | 区分临时效果、最终素材与真实完成状态，不虚报完成 |
| 倾向轻量自定义流程，已有技术栈偏好 | 不强制 Next.js，不预装全套多 Agent，不为小改动制造文档 |
| 需要交接、换 Agent 或隔天继续 | 只在复杂或跨会话任务留下任务记录、真实检查结果和下一步 |

历史个人站“余音·代码与声音”可以作为部署交付的场景；石像交互可作为验收约束的场景。它们当前是否上线、素材是否齐全，需要回到项目检查，不能由本手册保证。

## 2. 仓库怎么选：吸收方法，按需要安装工具

| 项目 | 对你的价值 | 本包采用与暂缓 |
| --- | --- | --- |
| [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) | 从理解上下文、开发、排错到审查的工程流程 | 采用按需读资料、基于源码、按风险验证、约束驱动的做法；先不用全部 25 个 Skill |
| [mattpocock/skills](https://github.com/mattpocock/skills) | 需求追问、领域词汇、拆解、复盘 | 采用少量关键追问、项目词汇表、把反复出错的问题变成检查；不为小需求强制长篇 PRD |
| [msitarzewski/agency-agents](https://github.com/msitarzewski/agency-agents) | 架构、后端、RAG、API 测试等角色视角 | 把视角转成按需检查项；不把角色文件数量当成协作能力，不预装整套“虚拟公司” |
| [rtk-ai/rtk](https://github.com/rtk-ai/rtk) | 压缩终端输出，减少进入上下文的噪声 | 可第二阶段单独试；不随包下载/启用，不压缩唯一排错证据 |
| [ruvnet/ruflo](https://github.com/ruvnet/ruflo) | 多 Agent 编排、记忆、工具层 | 当前暂缓；只有长期存在可拆分任务且协作收益可测，才做独立试点 |

原文里的 Star 数和“榜前四”没有可信统计口径，本手册不以此排序。RTK 声称的 60–90% 主要针对所处理命令的输出 Token，不能直接推成总账单下降比例；Claude 内置读取/检索工具不必然经过 Bash Hook。Agent 人设和 Markdown Skill 都是行为指导，不是强制执行的权限或测试闸门。

还做了两处适配：允许排错所需的充分阅读，控制的是无关修改；API 性能阈值根据业务基线和目标制定，不照搬统一 P95 < 200ms，尤其是 LLM 流式接口。

## 3. 每次任务先分清意图

你不必写很长提示词。用普通话或显式前缀，给目标和必要约束即可。

| 任务 | 可以直接复制的开场 | 预期结果 |
| --- | --- | --- |
| 新功能 | `/yuyin-dev 功能 给知识库查询加来源展示，沿用现有接口和页面。先确认边界，再实现、验证。` | 查现状→明确验收→小步实现→检查差异与测试 |
| Bug | `/yuyin-dev 修复 企业微信回调重复入库。保留正常回调行为，查原因并补必要回归。` | 复现→定位→修复→验证失败路径与旧行为 |
| 可行性 | `/yuyin-dev 评估 当前中间层能不能加人工接管？先不改代码，讲清接入点、约束和最小方案。` | 基于代码判断能加/有条件/暂缓，不偷偷实施 |
| 已有逻辑 | `/yuyin-dev 逻辑 从 Controller 到 Service/Mapper 梳理这条消息处理链，指出重试和状态变化。` | 入口、调用链、分支、数据变化、异常与代码定位 |
| 评估优化 | `/yuyin-dev 优化 看看 RAG 查询延迟是否值得优化，只评估；先找测量基线。` | 找瓶颈、证据、方案、代价和验证方式 |
| 实施优化 | `/yuyin-dev 优化 实施已确定的缓存方案，保持租户隔离与结果语义，测前后基线。` | 有授权地改代码，给可比较结果 |
| 审查 | `/yuyin-dev 审查 看当前 diff，优先找影响行为、权限和数据的问题。` | 实质问题、触发条件、后果和建议；没有就直说 |
| 交接 | `/yuyin-dev 交接 整理当前状态，让另一个 Agent 明天能接着做。` | 已做/未做、代码状态、真实检查结果、阻塞与下一步 |
| 复盘 | `/yuyin-dev 复盘 这次反复踩坑在哪里，最多提出三项可落实的流程改进。` | 优先变成测试、lint、脚本或环境配置，少堆永久规则 |

Codex 把前面的 `/yuyin-dev` 换成 `$yuyin-dev`。自动触发不稳定时显式调用，不能只凭“装了”假定每轮都生效。

遇到小问题，不必走满全部步骤。大型功能才建立 `.ai-dev/tasks/<任务名>.md`。用户已经授权的普通实现持续推进；生产部署、数据迁移等按项目和已有授权处理。

## 4. 一条任务的工作标准

**先读项目。** 检查适用规则和 Git 状态，找到真实依赖版本、入口与参照实现。已有未提交改动不能顺手覆盖。Java 看构建文件和实际 DTO/VO，前端看 package.json 与锁文件；不能把习惯框架当成当前框架。

**只问影响正确性的缺口。** 例如匿名分享是否允许、失败后是否重试、哪些用户能操作。可以从源码查到的字段、路由、构建命令由 Agent 自己查。默认建议和取舍放在一起，少打断工作。

**把“完成”写成行为。** 新功能通常写 1–3 条：成功场景、重要失败场景、已有行为保持。石像点击后应原地恢复，不能仅说“页面做好”；重复回调应只产生一次业务副作用，不能仅说“加了去重字段”。

**按闭环实施。** 优先完成一个可验收入口到结果的路径，再扩展。不顺手迁框架、改命名、抽象全部模块。必要的根因修复可以跨文件；“最小改动”不等于只改一行。

**按风险检查。** 小文案/样式无需为了流程写测试；权限、租户、重试、幂等、模型协议转换必须验证关键失败路径。只在新变化或失败出现时扩大检查范围。不能降阈值、删断言或跳过测试把失败包装成通过。

**简洁交付。** 默认四项：改动行为、关键原因、实际检查命令/结果、剩余限制。只要下一步时就给下一步。明确区分未提交、已提交、已推送、已部署；Mock 通过不能说真实联调成功。

## 5. 你常做的领域，优先看这些

| 场景 | 首要判断与验证 |
| --- | --- |
| 企业微信 / 原生微信 / 云手机 RPA | 确认官方能力、中间层还是界面自动化；权限、消息来源、幂等、顺序、重试与人工接管；三种入口不能混成一套承诺 |
| Java 后端 | 沿现有 Controller-Service-Mapper 结构；事务、DTO/VO 转换、分页、租户与软删除；用真实构建版本验证 |
| CPA/LLM 网关 | 模型名与路由、协议映射、流式事件、错误透传、重试；保留 Hermes prompt 指纹 workaround，逐步对照定位持久修复 |
| RAG 知识库 | 分开测检索、重排、生成；权限过滤、更新/失效、引用与无答案；重试不要放大成本或重复副作用 |
| 个人站 / Three.js 交互 | 真正点击、状态变化、不同视口、素材加载与降级；临时素材验收与最终素材交付分开记录 |
| Docker / 内网部署 | 实际容器、端口、卷、环境变量、架构与镜像版本；启动成功不足以证明业务 API 可用 |

字段、阈值、架构必须从具体项目确认。这些是查漏方向，不是对你当前系统实现的断言。

## 8. 一周试用如何判断是否改善

先跑三种真实任务：一个 Bug、一个功能、一次只读评估。不为了统计大量填表，只在复杂任务末尾记一句结果：有没有误改、重复解释、未经执行的“通过”、额外改动，检查是否更明确。

复盘时最多做三项改进。经常重复忘记启动命令，把正确命令写入 project.md；同一回归出现两次，补项目测试；经常格式错误，用 formatter/lint；领域说法混乱，再补 glossary.md。比持续加长全局提示词更可维护。

通过标准不是“装了多少 Skill”，而是少返工、评估不误实施、旧逻辑有定位依据、修复有回归证据、交接可直接继续。如果没有改善，删掉无效流程，保留真正有用的项目检查。
