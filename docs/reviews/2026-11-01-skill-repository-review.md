## 1. 结论

当前仓库适合继续受控试用，但应先修正示例中的正确性问题，再扩大使用或自动更新范围。现有证据尚不足以证明它稳定提高了开发准确性和效率。

仓库的来源锁定、安装校验、项目适配和验证边界做得比较扎实。主要问题集中在三个方面：

1. 部分上游示例本身有缺陷，可能被代理直接用于生成代码或验收。
2. 发布流程允许未经行为验收的新指令进入发行包。
3. 当前评测尚不能衡量技能的实际增益，也不能充分支持跨版本回归判断。

继续增加原则性说明，对这些问题的帮助有限。优先工作应是修正示例、补充针对性回归，以及建立有对照组的行为评测。

本报告使用以下优先级：

- **P1**：建议在扩大使用或下一次相关发布前处理。
- **P2**：应纳入近期改进。

优先级同时考虑触发条件与后果，不代表问题已经在实际业务项目中发生。报告明确区分代码缺陷、发布策略风险、评测设计缺口和条件性风险。

## 3. 直接影响生成代码与验收准确性的问题

### R1 · P1 · Node 更新示例允许请求字段名改变 SQL 结构

**性质：确定缺陷，已通过内存复现。**

证据：[Node details.md](../../skills/upstream/wshobson/nodejs-backend-patterns/references/details.md)，第 140–145、205–206、261–276、365–370 行。

示例从 Controller 将 `req.body` 传到 Service 和 Repository，再通过 `Object.keys(updates)` 拼接更新列名。值使用参数占位符，列名没有白名单。`UpdateUserDTO` 类型声明不会在运行时过滤请求字段。

本轮提取原方法体，以模拟数据库捕获生成的查询。包含特殊字段名的对象实际生成了：

```sql
UPDATE users
SET name = 'injected', email = $2, updated_at = CURRENT_TIMESTAMP
WHERE id = $1
RETURNING *
```

这证明输入能够改变 SQL 结构。实际数据库影响取决于表结构及调用权限；本轮没有连接数据库。普通额外字段同样可能造成非预期字段更新。

同文件的校验中间件丢弃了 `parseAsync` 的返回结果，不能据此认定下游使用的是清理后的数据。

**最小修正：**

- 使用可更新字段白名单和固定列名映射。
- 将验证后的结果交给业务层，敏感字段单独处理。
- 明确空更新是拒绝还是无操作。

**验收：**覆盖未知字段、特殊字段名、敏感字段和空对象；确认输入不能改变 SQL 结构或更新未授权字段。先建立失败用例，再修正示例。

### R2 · P1 · Node 缓存装饰器会在不同服务之间串读数据

**性质：确定缺陷，已通过内存复现。**

证据：[advanced-patterns.md](../../skills/upstream/wshobson/nodejs-backend-patterns/references/advanced-patterns.md)，第 363–373 行。

缓存键只有：

```typescript
`${propertyKey}:${JSON.stringify(args)}`
```

当 `UserService.getById(1)` 和 `OrderService.getById(1)` 共用缓存时，二者都使用 `getById:[1]`。

子审计提取原装饰器、去除 TypeScript 类型声明，并使用内存 `CacheService` 运行。先查询用户，再查询订单，第二次实际返回用户对象。这个错误不需要并发就能触发。

如果租户或用户身份存在于实例状态中，没有出现在参数里，还可能跨隔离边界串读。这是有条件的风险，本轮未在真实多租户系统或 Redis 中验证。

**最小修正：**显式提供稳定的服务命名空间和缓存键生成函数，将影响结果的隔离上下文纳入键。实例状态无法完整表达时，不套用此通用装饰器。

**验收：**覆盖跨服务、跨实例、跨租户，以及 `false`、`0`、空字符串等合法缓存结果。

### R3 · P1 · React 规则错误描述 transition 的中断能力

**性质：源码与官方文档共同支持的内容缺陷，未执行真实 React 页面测试。**

证据：[rendering-usetransition-loading.md](../../skills/upstream/vercel/react-best-practices/rules/rendering-usetransition-loading.md)，第 51–55、73 行。

推荐示例将请求放进 `startTransition(async () => …)`，请求后直接 `setResults`，并声称新 transition 会自动取消之前的 pending transition。代码没有处理请求乱序。

触发场景是用户先搜索 A、再搜索 B，B 先返回，A 后返回，最终结果可能被 A 覆盖。React 官方文档说明，此类自定义异步处理需要自行处理请求顺序；当前 `await` 后的状态更新也需要额外包裹 `startTransition` 才能标记为 transition。参见 [React 官方 useTransition 文档](https://react.dev/reference/react/useTransition)。

旧示例同样存在竞态。本项问题是推荐规则作出了不成立的保证，并给出不完整实现，不能表述为推荐版首次引入了所有竞态。

**最小修正：**明确适用版本，删除自动取消的误导性描述，使用项目现有请求机制或请求序号淘汰过期结果，并正确处理 `await` 后的状态更新。

**验收：**以可控请求顺序覆盖旧请求后返回、请求失败及 pending 状态；分别核对项目支持的 React 版本。

### R4 · P1 · 浏览器辅助脚本可能把旧服务当成本次服务验收

**性质：确定缺陷，已通过内存模拟复现控制流程。**

证据：[with_server.py](../../skills/upstream/anthropic/webapp-testing/scripts/with_server.py)，第 23–32、69–89 行。

脚本将目标端口可连接作为服务就绪条件，没有检查新启动进程是否退出，也没有确认连接的是本次服务。

本轮直接加载原脚本，以内存模拟表示“新进程已失败退出，但旧服务仍监听端口”。结果如下：

- 仍执行测试命令。
- 打印 `Server ready`。
- 最终退出码为 `0`。
- 没有检查新进程存活状态。

这可能使截图、交互测试甚至最终验收针对旧页面。这里证明的是控制流程缺陷，没有进行真实端口冲突或浏览器实验。

附属静态观察：stdout/stderr 使用 PIPE 却不消费，存在高日志量阻塞风险；清理仅终止 `shell=True` 启动的 shell，不能据此证明子进程全部退出。这两点需要在修复同一辅助器时动态验证。

**最小修正：**启动前检查端口占用，等待期间检查进程退出并提供错误上下文，验证本次应用的健康标识；正确消费日志和清理进程组。

**验收：**覆盖端口已占用、启动立即失败、慢启动、高日志量，以及退出后的端口释放。

### 上游内容修正方式

R1–R4 应通过仓库的声明适配和快照重建流程修正，保持来源可追溯。不宜直接修改快照后重新计算摘要来绕过校验。建议同步维护对应反例，避免后续上游更新重新引入问题。

## 4. 长期准确性与改进判断的缺口

### R5 · P1 · 自动发布会获取未经行为验收的新上游指令

**性质：已核实的发布策略风险，仓库已披露其限制。**

证据：[release.mjs](../../scripts/release.mjs)，第 21–35 行；[行为变化报告](../../evals/upstream-changes.json)。

实际流程为：

```text
发布准备 → 同步最新上游 → 机械测试与 verify → 提交快照 → 生成候选并发布
```

一次原本只想发布自有修改的操作，也可能带入新的上游行为指令。许可、摘要和脚本白名单能够约束来源与文件身份，但无法证明 Markdown 中的新建议正确。

当前行为报告包含 5 个受影响案例、30 个 pending 项，以及未覆盖的 `frontend-design`，发布验证仍可通过。仓库对此有明确披露，因此这是质量策略风险，不能说成伪造验收。

**最小修正：**将上游更新形成独立、可审阅的候选；发布使用已审阅的锁定内容。按变化影响运行最小行为回归，低风险纯文档变更可以记录豁免依据，无需每次跑满所有组合。

**验收：**未经审阅的行为变化不能直接进入正式发行；已有候选恢复仍使用原始字节，不重新拉取上游。

### R6 · P2 · 现有评测无法判断技能是否提高准确性与效率

**性质：评测设计缺口，不否定已有冒烟记录的价值。**

证据：[manifest.json](../../evals/manifest.json)，第 32 行起；[evals.mjs](../../scripts/evals.mjs)，第 182–193 行。

主要原因：

1. 没有不使用技能的对照组。
2. 提示中反复明确“保留原栈、不安装依赖、只做局部修改”，这些约束本身就可能解释良好表现。
3. 每例只安装指定技能，而普通安装默认提供全部 9 个技能，尚未充分检验实际环境中的技能竞争、误触发和选择成本。
4. 没有汇总耗时、工具调用、上下文读取、澄清轮次或返工等效率指标。

这些用例适合检查明确约束下是否越界，但不足以衡量自然请求下的路由准确率，也无法将任务成功归因于技能。

根据[冒烟记录](../../evals/runs/2026-10-15-smoke.json)，现有覆盖如下：

| 项目 | 仓库记录 |
| --- | --- |
| 理论组合 | 6 案例 × 2 宿主 × 3 调用方式＝36 |
| 尝试次数 | 15 |
| 完成次数 | 13，含一次复测 |
| 唯一完成组合 | 12，覆盖 33.3% |
| 真实浏览器验收 | 未完成 |
| React 实际页面验收 | 未完成 |
| Java / MyBatis / 目标数据库联调 | 未完成 |
| `frontend-design` 独立行为 | 未覆盖 |

33.3% 是组合覆盖率，不是成功率。部分直接调用缺少独立的技能读取证据。首次 Claude 浏览器案例存在未经检查即断言系统浏览器缺失的问题，原始记录被保留，随后做了一次针对性复测；不能据此推断所有模型都已避免同类问题。

**最小修正：**在相同模型配置下设置无技能、仅 `yuyin-dev`、完整组合三个实验组；同时保留明确约束用例和自然短请求用例，加入应当不触发技能的负例。各组重复运行，分别报告正确率、越界率、返工和成本。

**验收：**能够识别哪些任务因技能改善、哪些退化，以及相应时间与上下文成本；不以单次任务成功替代效果归因。

### R7 · P2 · 自有入口没有纳入行为证据失效机制

**性质：已核实的回归追踪与证据可复核性缺口。**

证据：[behavior.mjs](../../scripts/behavior.mjs)，第 12–39、42–55 行；[smoke 摘要](../../evals/runs/2026-10-15-smoke.json)，第 4–5 行。

当前行为报告比较上游 lock 与案例定义，路径验证只接受 `skills/upstream/`。修改以下核心文件，不会通过这套机制重新标记受影响案例：

- `yuyin-dev/SKILL.md`
- `references/stack-skills.md`
- 自有功能、修复、评审等参考

最可能改变任务路由和执行边界的修改，缺少对应的行为回归追踪。

另外，仓库中的冒烟摘要使用 `<EVAL_ARTIFACT_ROOT>` 占位符，未提供可定位的原始证据入口。本次只能核对摘要统计，不能独立重新审阅全部 trace；这不等于认定记录不真实。原始运行结果按脚本设计记录技能和验收器摘要，但这些身份信息没有完整进入仓库中的汇总索引。

本次检查没有发现可据以宣称“冒烟之后技能字节已经变化”的证据；此项描述的是失效机制缺口，不能据此直接认定现有样本过期。

**最小修正：**让行为证据绑定自有及上游技能摘要、fixture、验收器和实际模型配置，提供脱敏证据包的稳定索引。不需要将凭证或私有原始日志提交到公开仓库。

**验收：**只修改主入口时，相关证据标为待复测；无关 README 修改不使全部行为证据失效；审阅者能够定位对应的脱敏原始证据。

## 5. 安装与分发缺陷

### R8 · P2 · 源码组合安装遗漏锁文件符号链接检查

**性质：确定的预检遗漏，通过静态写入调用链核实，未执行覆盖实验。**

证据：[profiles.mjs](../../scripts/profiles.mjs)，第 95–112、165–166、195 行；对照 [npm 入口](../../bin/yuyin-skills.mjs)，第 111–113 行。

组合安装只检查 `.agents`、`.claude` 及技能目标目录，遗漏项目根目录的 `skills-lock.json` 符号链接。固定的 `skills@1.7.2` 会写入项目锁文件。

触发条件：目标项目的锁文件链接到项目外可写文件，且所选技能尚未安装。底层 CLI 写锁时可能跟随链接覆盖外部文件。npm 主入口已有这项防护，两个入口行为不一致。

**最小修正：**复用统一的安装预检，覆盖锁文件及其父路径。

**验收：**以隔离哨兵文件作为链接目标，要求调用 CLI 前拒绝安装，且哨兵内容保持不变。

### R9 · P2 · 仅修改 npm 入口不会触发自动发布

**性质：确定的发布触发缺陷，通过工作流与分发清单静态核对。**

证据：[publish.yml](../../.github/workflows/publish.yml)，第 6–24 行；[package.json](../../package.json)，第 17 行。

发布触发路径遗漏 `bin/**`。仅修复正式分发的 `bin/yuyin-skills.mjs` 并合入 main，不会触发自动发布，npm 用户继续使用旧入口。发布脚本自身能够识别该内容变化，但工作流没有机会启动。

**最小修正：**增加该路径，并校验所有分发文件均被发布过滤器覆盖。

**验收：**只修改 `bin/yuyin-skills.mjs` 的变更也符合发布过滤条件。无需触发真实 npm 发布即可测试过滤器覆盖。

### 后续可重复性改进

以下是设计改进项，不与前述确定缺陷混为一谈：

- [安装指南](../installation.md)中的更新方式使用未固定版本的 `npx skills`。首次安装使用固定工具，但更新和回退不一定使用相同版本。建议明确调用包内固定 CLI，或显式固定工具版本。
- 项目安装记录主要保留本地来源路径，缺少本包版本的直接身份记录。`npx` 缓存清理或换机器后，来源路径可能不可用。已安装内容仍是独立副本，问题在于来源追踪和重建。建议提供只读状态检查，显示实际安装的包版本、技能集合和内容摘要。

## 6. 效率与结构建议

### 值得保留的设计

- `yuyin-dev` 按意图拆分参考，区分只读分析与实施，避免自动创建文档。
- 专业技能已经加入兼容性说明，直接调用也能读到；“直接调用完全绕过适配”不成立。
- Spring 参考对事务、并发、MyBatis 和验证层次的说明具体。
- 安装后核对实际资源字节，上游保留提交、摘要和许可证据。
- 自动检查不把进程退出 0 当作行为成功，原始失败与人工纠正分开保存。
- 模型生成的 JavaScript 和浏览器测试默认不会在父验收器中直接执行，可信 fixture、SQL 样例和真实集成的边界有明确说明。

### 可测量的上下文优化

[javascript-testing-patterns/SKILL.md](../../skills/upstream/wshobson/javascript-testing-patterns/SKILL.md) 约 541 行、15 KB，入口包含大量完整示例。可借鉴 Node 技能，将入口保留为选择规则和导航，把具体框架示例按需披露。

应测量实际读取量、任务成功率和返工后再判断收益，不能仅凭文件缩短宣称效率提升。

React 编译版 `AGENTS.md` 虽然较大，现有入口支持逐规则读取，不能直接把它全部算作每次调用的上下文成本。
